# Auth Practice

회원가입, 로그인, 인증/인가, 기본적인 웹 보안 기법을 **직접 구현하며 학습**하는 연습 프로젝트입니다.
프론트엔드(JavaScript)와 백엔드(FastAPI) 사이에서 데이터가 오가는 흐름을 이해하고, 보안 기능을 단계별로 적용하는 것을 목표로 합니다.

> ⚠️ **학습용 프로젝트입니다.** 실제 서비스에 그대로 사용하지 마세요. 실제 개인정보나 금융정보를 입력하지 말고, 반드시 가상의 데이터만 사용하세요.

## 프로젝트 목표

1. **요청의 흐름 익히기**: 브라우저 → API 서버 → 저장소 → 응답 → 화면 반영의 전체 흐름을 직접 구현하고 설명할 수 있게 된다.
2. **인증과 인가 구현**: 비밀번호 해시, 토큰 기반 인증, 권한 검사를 직접 만들어 본다.
3. **보안 사고방식 기르기**: 내가 만든 코드를 직접 공격해 보고 방어하는 경험을 쌓는다.
4. **개인정보 처리 감각**: 마스킹, 암호화, 로그 관리, 삭제 처리 등 개인정보 보호의 기본기를 연습한다.

## 단계별 로드맵

### 1단계. 회원가입 + 비밀번호 해시 저장 ✅

**구현 기능**
- 회원가입 폼 (아이디, 비밀번호, 비밀번호 확인)
- 서버 측 입력값 검증 (아이디 형식, 비밀번호 길이/조합)
- 아이디 중복 검사 (대소문자 구분 없음)
- bcrypt로 비밀번호 해시 후 저장 (원문은 저장하지 않음)
- 응답에 해시를 포함하지 않음

**학습 포인트**
- `submit` 이벤트, `preventDefault`, `fetch` POST
- Pydantic 요청 모델, `HTTPException`, 상태 코드(201, 400, 409)
- 해시와 salt의 개념
- 프론트 검증은 편의용, **백엔드 검증이 실제 방어**라는 원칙

### 2단계. 로그인 + JWT 토큰 발급

**구현 기능**
- `POST /api/auth/login`: 아이디/비밀번호 검증 후 JWT 발급
- 토큰 만료 시간 설정
- 로그인 실패 시 아이디/비밀번호 중 무엇이 틀렸는지 구분하지 않는 통일된 에러 메시지
- 프론트: 토큰 보관, 이후 요청의 `Authorization: Bearer` 헤더 첨부

**학습 포인트**
- 토큰 기반 인증의 흐름과 서명 검증
- 토큰 보관 방식 비교: `localStorage` vs `HttpOnly` 쿠키 (XSS와 CSRF 관점)
- `bcrypt.checkpw`를 이용한 비밀번호 검증
- 401 상태 코드의 의미

### 3단계. 인증이 필요한 API와 권한 검사

**구현 기능**
- FastAPI `Depends`로 "현재 로그인한 사용자" 의존성 구현
- 게시글 작성/수정/삭제는 로그인 사용자만 가능
- 수정/삭제는 **작성자 본인만** 가능
- 프론트: 비로그인 시 UI 제한, 401 응답 시 로그인 페이지로 이동

**학습 포인트**
- 인증(Authentication)과 인가(Authorization)의 차이
- 401(미인증)과 403(권한 없음)의 구분
- 프론트에서 버튼을 숨기는 것은 보안이 아니며, **서버 검증이 필수**임을 확인

### 4단계. 직접 공격해 보고 방어하기

> 반드시 **본인의 로컬 환경에서만** 진행합니다. 타인의 서비스에 시도하는 것은 불법입니다.

| 공격 | 시도 방법 | 방어 |
|---|---|---|
| XSS | 입력값에 `<script>` 삽입 | 출력 시 이스케이프, `textContent` 사용 |
| 권한 우회 | 타인의 글 ID로 직접 DELETE 요청 | 작성자 일치 검사 |
| 토큰 위조 | 토큰 일부 변조 후 요청 | 서명 검증, 만료 확인 |
| 무차별 대입 | 로그인 반복 시도 | 실패 횟수 제한 |
| 검증 우회 | 프론트를 거치지 않고 API 직접 호출 | 백엔드 검증 |

### 5단계. 보안 기능 추가

- 로그인 실패 횟수 제한 및 일시 잠금
- 보안 로그 기록 (로그인 성공/실패, 시각) 및 **기록하지 말아야 할 정보** 정의
- 개인정보 마스킹 (이메일, 전화번호 등)
- 민감 정보 암호화 저장 (`cryptography`의 Fernet)
- CORS 허용 출처 제한 (적용 완료, 배포 환경에 맞춘 재점검)

### 6단계. 확장 과제 (선택)

- 비밀번호 변경, 회원 탈퇴 (개인정보 파기 처리)
- OTP 기반 2단계 인증 (`pyotp`)
- 역할(role) 기반 접근 제어 (일반 사용자 / 관리자)
- 모의 송금 앱: 잔액 조회, 이체, 이중 이체 방지, 금액 검증, 거래 로그 (가상 데이터만 사용)
- JSON 파일에서 SQLite로 저장소 전환

### 최종 단계. UI 디자인

- 모든 기능 완성 후 CSS 적용
- 에러/성공 메시지, 폼 레이아웃 정리

## 시작하기

### 사전 준비

- Python 3.12 이상
- VS Code + Live Server 확장

### 설치 및 실행

```bash
# 1. 저장소 클론
git clone <저장소 주소>
cd auth_practice/backend

# 2. (권장) 가상환경 생성 및 활성화
python -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # Mac/Linux

# 3. 의존성 설치
pip install -r requirements.txt

# 4. 서버 실행
uvicorn main:app --reload
```

서버 주소: `http://127.0.0.1:8000`
API 문서(Swagger UI): `http://127.0.0.1:8000/docs`

### 프론트엔드 실행

1. VS Code에서 `frontend/signup.html`을 연다.
2. 우클릭 → **Open with Live Server**
3. 주소가 `http://127.0.0.1:5500`인지 확인한다.

> Live Server 포트가 다르면 `backend/main.py`의 `allow_origins`를 해당 주소로 수정하세요. 맞지 않으면 브라우저 콘솔에 CORS 에러가 발생합니다.
> 서버를 먼저 실행한 뒤 프론트를 열어야 합니다.

## API 명세

공통 prefix: `/api/auth`

### 회원가입

`POST /api/auth/signup`

**Request Body**

```json
{
  "username": "test_user1",
  "password": "abcd1234"
}
```

**검증 규칙**

| 항목 | 규칙 |
|---|---|
| username | 영문, 숫자, 밑줄(`_`) 4~20자 |
| password | 8자 이상, 72바이트 이하, 영문과 숫자 각각 1자 이상 포함 |

**Response**

| 상태 코드 | 의미 | 본문 예시 |
|---|---|---|
| `201 Created` | 가입 성공 | `{"id": 1, "username": "test_user1"}` |
| `400 Bad Request` | 아이디/비밀번호 규칙 위반 | `{"detail": "비밀번호는 8자 이상이어야 합니다."}` |
| `409 Conflict` | 이미 사용 중인 아이디 | `{"detail": "이미 사용 중인 아이디입니다."}` |
| `422 Unprocessable Entity` | 요청 본문 형식 오류 | FastAPI 기본 에러 |

### 예정된 API

| 메서드 | 경로 | 설명 | 단계 |
|---|---|---|---|
| POST | `/api/auth/login` | 로그인, JWT 발급 | 2 |
| GET | `/api/auth/me` | 현재 로그인한 사용자 정보 | 3 |
| GET | `/api/posts` | 게시글 목록 | 3 |
| POST | `/api/posts` | 게시글 작성 (로그인 필요) | 3 |
| PUT | `/api/posts/{id}` | 게시글 수정 (작성자만) | 3 |
| DELETE | `/api/posts/{id}` | 게시글 삭제 (작성자만) | 3 |

## 데이터 모델

### users.json

```json
[
  {
    "id": 1,
    "username": "test_user1",
    "passwordHash": "$2b$12$...",
    "createdAt": "2026-11-25T00:00:00+00:00"
  }
]
```

- `passwordHash`는 bcrypt 해시이며, 원문 비밀번호는 어디에도 저장하지 않습니다.
- API 응답에는 `passwordHash`를 절대 포함하지 않습니다.

## 개발 원칙

1. **기능 먼저, 디자인은 나중에**: CSS는 모든 기능이 끝난 뒤 적용한다.
2. **프론트는 믿지 않는다**: 모든 검증과 권한 검사는 서버에서 최종 수행한다.
3. **최소한의 정보만 저장하고 노출한다**: 불필요한 개인정보는 받지도, 저장하지도, 응답하지도 않는다.
4. **작은 단위로 확인한다**: `/docs`로 API를 먼저 테스트하고, 그다음 프론트를 연결한다.
5. **흐름을 설명할 수 있어야 한다**: 기능을 만든 뒤 요청이 어떻게 흐르는지 말로 설명해 본다.

## 알려진 제한 사항

- JSON 파일 저장은 동시 요청 시 데이터가 꼬일 수 있습니다. (이후 SQLite 전환 검토)
- 로컬 개발 환경에서는 HTTP를 사용합니다. 실제 서비스에서는 HTTPS가 필수입니다.
- 학습용 구현이므로 이메일 인증, 비밀번호 재설정, 계정 복구 등은 포함하지 않습니다.
